# OmniChat v3 phase 3: tools/plugins, web search, history search, backup, titles (extends PROTOCOL-v3.md and PROTOCOL-v3-phase2.md)

Spec items: 3 plugins, 8 web search, + proposals (full-text search, backup/export, auto title, per-model generation params). Developer features still open (model compare, benchmark, structured output, template editor, token view, config-as-files, CLI) are NOT in this round.

## 1. Tools (the "plugin" layer of the harness)
```ts
type ToolPermission = "network" | "filesystem-read" | "filesystem-write" | "shell";
interface ToolManifest { name: string /* [a-z0-9_]{1,40} */; description: string; parameters: object /* JSON Schema of the arguments */; permissions: ToolPermission[] }
interface ToolInfo extends ToolManifest { source: "builtin" | "plugin"; pluginId: string | null; available: boolean; error?: string; needsApproval: boolean }
interface ToolCall { id: string; name: string; arguments: any; status: "pending" | "running" | "done" | "error" | "denied"; result?: string /* truncated to 8 KB */; error?: string; durationMs?: number; startedAt: number }
interface SearchSource { index: number /* 1-based, as cited [n] */; title: string; url: string; snippet?: string }
// Message gains: toolCalls: ToolCall[] | null; sources: SearchSource[] | null
// Conversation/Project gain: tools: string[] | null (null = inherit; [] = none); searchMode: "off" | "auto" | "always" | null
// Settings gains: tools: string[] | null; searchMode: "off" | "auto" | "always"; autoTitle: boolean (default true); titleModel: string | null ("<providerId>::<model>"); modelParams: Record<string /* "<providerId>::<model>" */, SamplingParams> | null
```
- Resolution for a turn: tools = conversation ?? project ?? settings ?? [] ; searchMode = conversation ?? project ?? settings ?? "off". Enabling a tool for a chat is NOT consent to run it (see approvals).
- `GET /tools` -> `{tools: ToolInfo[]}`; `POST /tools/reload` (admin) rescans plugins.
- **Built-in tool `web_search`** `{query: string}` (permissions ["network"]): available only when a search backend is configured (SEARXNG_URL). Returns numbered results `[n] title — url — snippet` (max `SEARCH_MAX_RESULTS`, default 5) and records `sources` on the message.
- **Plugin format**: directory `$DATA_DIR/plugins/<id>/` with `plugin.json` `{id, name, version, description, main: "index.mjs", tools: ToolManifest[]}` and an ES module exporting `tools: { [toolName]: async (args, ctx) => string | object }`; `ctx = { fetch /* only provided when the tool declares "network" */, signal, log(msg), userId, config: {} }`. Plugins run IN-PROCESS with the server's OS permissions (permissions are declarations for the approval UI, not a sandbox): document it loudly; plugins are managed by files + admin `POST /tools/reload`, never uploaded via API. Invalid manifests are skipped with `error` shown in `/tools`. Two example plugins ship in `plugins-examples/` (`current-time` no permissions, `fetch-url` network).
- **Tool-calling loop** (chat.ts, openai-compatible providers with `tools` support): send `tools` (OpenAI function format) for enabled+available tools; stream `delta.tool_calls`; when the model finishes with tool calls: for each call -> approval (below) -> execute -> append the assistant `tool_calls` message and `tool` result messages to the request -> continue streaming; at most `MAX_TOOL_ROUNDS` (6) rounds; unknown tool => tool error result. Only the FINAL assistant text becomes `content`; the trace is `toolCalls`; later turns re-send only final texts (traces are not replayed). The provider stream contract gains items `{kind:"tool_calls", calls:[{id,name,arguments(string)}]}`; `dsh-bridge` ignores tools.
- WS: server->client `{type:"tool", messageId, conversationId, call: ToolCall}` on every status change (also persisted in `message.toolCalls`, carried by `snapshot` and `upsert`).
- **Approvals** (table `tool_grants(user_id, tool_name, granted_at)`): a tool whose manifest has any permission needs a grant before it runs. If there is none the call becomes `pending` and the server sends WS `{type:"tool_approval", approvalId, messageId, conversationId, tool, arguments, permissions}`; the client replies `{type:"tool_approval_reply", approvalId, decision:"once"|"always"|"deny"}`; no reply within 120 s or the generation is stopped => `denied`. `always` stores a grant. `GET /tool-grants` -> `{grants:[{tool, grantedAt}]}`, `DELETE /tool-grants/:tool`. Tools with NO permissions never ask. A denied call returns a tool error result `denied by user` to the model.
- **Search modes**: `auto` = tool calling when the model accepts tools (if the backend rejects `tools` with an error, retry once without tools in `always` mode); `always` (also for models without tool calling) = before the request the server runs ONE search with the latest user message (trimmed to 200 chars; needs the same approval for `web_search`, shown as a pending ToolCall), injects the numbered results as an extra system block (`Search results … Cite sources as [n]; use only these results`), records `sources`; `off` = no search. A search failure never fails the reply: the error is recorded as a ToolCall `error` and the reply continues without results.
- Search backend interface `SearchBackend { name; search(query, {limit, signal}): Promise<SearchResult[]> }`, registry like providers; first implementation SearXNG: `GET {SEARXNG_URL}/search?q=…&format=json` (timeout `SEARXNG_TIMEOUT_MS` default 8000; clear error if JSON is disabled: "SearXNG returned HTML: enable `search.formats: [html, json]`"). `GET /search/status` (authed) -> `{configured, backend, host /* host:port only */, reachable, error?}`; `POST /search/test {query}` (admin) -> results.
- `GET /version` `searxng` stays "configured" boolean.

## 2. Auto title, per-model params
- Auto title: after the first assistant reply of a conversation whose title is still the default or the first-40-chars fallback, if `settings.autoTitle` and provider kind is openai-compatible: one short non-streamed call (model = `settings.titleModel` or the chat's own) "Write a title of 3-6 words for this conversation. Reply with the title only." -> trimmed, quotes/punctuation stripped, max 60 chars; PUT-style update + upsert broadcast; failures ignored; never blocks the reply.
- Per-model params: merge order becomes one-shot > conversation > project > `settings.modelParams[<providerId>::<model>]` > global. Included in the debug record's `final.params`.

## 3. Full-text history search
`GET /history/search?q=&projectId=&limit=20&offset=0` -> `{results:[{messageId, conversationId, conversationTitle, projectId, role, snippet /* plain text with the hit wrapped in \u0001…\u0002 markers, ~160 chars */, createdAt}], total}`. SQLite FTS5 with the `trigram` tokenizer (CJK substring search) over message content (+ reasoning excluded) joined to conversation title; queries shorter than 3 characters fall back to LIKE; owner only; excludes deleted conversations; triggers keep the index in sync; migration backfills existing rows; also searches conversation titles (result with `messageId: null`).

## 4. Backup and export
- Admin only: `POST /admin/backup` -> `{name, size, createdAt}` (SQLite `VACUUM INTO $DATA_DIR/backups/omnichat-YYYYMMDD-HHMMSS.db`); `GET /admin/backups` -> `{backups:[{name,size,createdAt}]}`; `GET /admin/backups/:name` (download, name validated); `DELETE /admin/backups/:name`. Scheduler: env `BACKUP_INTERVAL_HOURS` (default 24, 0 = off), `BACKUP_KEEP` (default 7, oldest pruned), first run 5 minutes after start if none exists in the interval. Restore is offline (documented in docs/INSTALL.md by the distribution docs later; the API does not restore).
- Export (owner): `GET /conversations/:id/export?format=md|json&branches=current|all` (default md/current; Markdown has `# title`, project, model, date, then `**You:** …` / `**Assistant:** …` with sources and a collapsed-style `> Thinking` block only if `?reasoning=1`), `GET /export` -> JSON `{version:1, exportedAt, projects, presets, settings, conversations:[{…, messages:[…]}]}` of all the caller's data (no tokens/keys/providers' apiKeys; providers listed WITHOUT keys). `Content-Disposition` attachment with a safe filename.
- Import: `POST /import` (body = the JSON export) creates projects/presets/conversations/messages under NEW ids (mapping parentId/headId/projectId), never overwrites, returns counts; refuses > 50 MB; settings are not imported.

## 5. Ownership
Server A (tools + search + titles + model params): chat.ts, providers/*, prompts.ts, sampling.ts, projects.ts (new fields), sync.ts serialisation, new tools/ (registry, builtin web_search, plugin loader, approvals), search/ (backend interface + searxng), migration file `migrate-tools.ts`, plugins-examples/, routes in `routes-tools.ts`, tests, PROTOCOL notes. Server B (history search + backup/export/import): new files only (`migrate-fts.ts`, `history-search.ts`, `backup.ts`, `export.ts`, `routes-history.ts`, tests) plus one registration line each in index.ts/db.ts. App A: tool call cards in messages (name, args, status, duration, result, denied), approval dialog, search toggle (off/auto/always) in the composer + project/chat/global settings, Sources list with clickable [n] citations, Tools screen (Settings > Tools: list from /tools, enable per global/project/chat, grants list with revoke, search status), auto-title + per-model params settings. App B: History search screen (Settings or header search icon; highlights; opens the conversation scrolled to the message), Backup screen (admin only: create/list/download/delete, schedule info), Export/Import (conversation menu: Export Markdown/JSON; Settings: export all, import file). Both must degrade gracefully against old servers.

## 6. Server B implementation notes (history search, backup, export/import)
- SQLite 3.53.3 bundled with node:sqlite (Node 24.19) supports FTS5 and the `trigram` tokenizer (verified incl. CJK/emoji). `migrate-fts.ts` falls back to `unicode61` + LIKE if trigram were missing (`fts_meta.tokenizer`).
- Index: standalone FTS5 table `fts_history` keyed through `fts_map(fid, kind m|c, id)` (TEXT-pk rowids are not stable across VACUUM, so no external-content table). Messages are indexed once they leave `streaming` (content/status updates re-index); titles indexed as kind `c`. Backfill runs on every start (idempotent).
- `/history/search`: whitespace-separated terms (max 8, query max 200 chars) are ANDed; terms >= 3 code points go through FTS as quoted phrases (no FTS syntax ever reaches SQLite), shorter terms are `LIKE` filters (case-insensitive for ASCII only). Results newest first (not bm25). Title hits: `messageId: null`, `role: null`, `createdAt` = conversation updatedAt. `limit` clamped 1..100.
- Backup: names `omnichat-YYYYMMDD-HHMMSS[-N].db` (local time); pruning to `BACKUP_KEEP` happens after EVERY backup (manual too). Scheduler checks hourly (or the interval if shorter); `BACKUP_FIRST_DELAY_MS` (test hook, default 300000). Started from `registerHistoryRoutes`, so index.ts needs no extra line. `VACUUM INTO` is synchronous (briefly blocks the event loop on big databases).
- Export: single-conversation JSON uses the same envelope as `/export` (`{version, exportedAt, projects, presets:[], conversations:[...]}`) so it can be re-imported; `reasoning` is only included with `?reasoning=1` there, always in `/export`. `branches=all` Markdown marks siblings as `*[Branch i/n]*` and indents alternative branches with `>`. Message `sources` are exported/imported when the column exists (Server A).
- Import: `POST /import` -> `{projects, presets, conversations, messages}` (counts). Whole payload validated first, written in one transaction (400 on any structural error, nothing written); `providerId`/`defaultProviderId` are kept only if the importer owns that provider, `projectId` only if the project is in the payload; `streaming` status becomes `done`; message parent cycles/duplicate ids are rejected, dangling parents become roots; metrics, tool calls, tools/searchMode fields are not imported. Body limit 50 MB (413 above).

## 6. Implementation notes (Server A) - deviations and details
- Search mode vs tools: `web_search` is governed by `searchMode` only (offered as a tool only in `auto`; `always` uses the server-side pre-search; `off` never). A `web_search` entry in `tools` is ignored; other enabled tools are offered in every mode. Providers other than `openai-compatible` get no tools, no search and no auto title.
- `always`: the numbered results are MERGED into the first system message (or become one) as a block `Search results for the user's latest message:\n[1] ...\n\nCite sources as [n]; use only these results.` (several system messages break some chat templates). Not injected when there are no results. The block is part of the debug `final.messages`; context accounting (`enforceContext`) does not count it.
- `auto` fallback trigger: the first request fails before any output with HTTP 400/404/405/415/422/500/501 or an error text mentioning tools/function calling; ONE retry without tools, with the `always` search when `web_search` was offered. 401/403/429 and connection errors are not retried. Debug: `final.tools.fellBackToAlways`.
- Intermediate text of a tool round is streamed as normal `delta`s; when the round ends in tool calls the server broadcasts a `snapshot` frame `{messages:[{id, conversationId, content:"", reasoning, status:"streaming"}]}` so clients REPLACE the content (only the final text is kept). Reasoning accumulates over all rounds. After `MAX_TOOL_ROUNDS` (6) tool rounds the next request is sent without `tools`.
- Metrics/usage of a message with tool rounds describe the LAST model request only (`prompt_tokens`, `completion_tokens`); ttft is measured from the first request.
- WS: `tool_approval` is broadcast to all devices of the user; any device may reply. When the user's last WS connection closes, pending approvals are denied. Approval timeout env `TOOL_APPROVAL_TIMEOUT_MS` (default 120000). Tool timeout env `TOOL_TIMEOUT_MS` (default 30000). `snapshot` entries carry `toolCalls` and `sources`.
- Plugins: `id` must equal the directory name and match `[a-z0-9][a-z0-9_-]{0,39}`; tool names are global (a duplicate of a builtin or earlier plugin is reported as unavailable with an error). An invalid manifest shows up in `GET /tools` as an unavailable pseudo entry whose `name` and `pluginId` are the directory name and `error` the reason; an import failure keeps the manifest tools listed with `available:false` and `error`. `ctx.config` is always `{}`. Plugin dir override env `PLUGINS_DIR` (default `$DATA_DIR/plugins`); the dir is created on load. `GET /tools` waits for the first scan. `POST /tools/reload` returns `{tools}`. Examples ship in `server/plugins-examples/`.
- `GET /search/status`: `reachable` = SearXNG answered HTTP at all (a JSON-disabled SearXNG is reachable with `error` set); result cached 5 s (env `OMNICHAT_SEARCH_STATUS_TTL_MS`). Not configured: `{configured:false, backend:null, host:null, reachable:false}`. `POST /search/test` -> `{results:[{title,url,snippet?}]}`, errors 400 (not configured / no query) or 502 `{error}`. SearXNG HTTP 403 gets the same hint as HTML. Env: `SEARXNG_URL`, `SEARXNG_TIMEOUT_MS` (8000), `SEARCH_MAX_RESULTS` (5, max 20). Sources are numbered per message and de-duplicated by URL across several searches.
- `DELETE /tool-grants/:tool` is idempotent -> `{ok:true}`. `settings.tools: null` = none; `settings.searchMode` default `off`; `settings.autoTitle` default true, overridable for the whole server by env `AUTO_TITLE_DEFAULT=0` (used by the test servers so existing tests do not see extra title requests; explicit user settings win).
- Auto title: runs only when the conversation title is still `New chat` or equals the first 40 chars of the first user message at both start and end of the call, and the conversation has exactly one `done` assistant message. The `<think>` blocks, the `Title:` prefix, quotes and trailing punctuation are stripped; `titleModel` is used only if the provider is the user's own, not deleted and openai-compatible.
- Per-model params: `buildContext` gets `providerId` (context.ts passes it) and merges `settings.modelParams["<providerId>::<model>"]` between project and global; `final.params` shows the result.
- Debug record `final` gains optional `tools {mode, offered, rounds, calls[], fellBackToAlways?}` and `search {mode, query, injected, sources, error?}`. For messages with tool rounds `final.messages` is the last request (incl. `tool` messages).
