# ツール・プラグインの作り方

モデルが呼び出せるツール(関数)を、サーバーに置くプラグインとして追加する手順です。仕様の根拠は [PROTOCOL-v3-phase3.md](../PROTOCOL-v3-phase3.md) の「1. Tools」と「6. Implementation notes (Server A)」、実装は `server/src/tools/registry.ts`、`tools/approvals.ts`、`tools/exec.ts` です。

> **警告: 既定では、管理画面から導入したプラグインは別プロセス(隔離実行)で動きます。手で置いたプラグインはサーバーのプロセス内で、サーバーの OS 権限のまま動きます。** 隔離の強さと限界は [セキュリティ](#セキュリティ) を読んでください。
> `plugin.json` の `permissions` は承認ダイアログに表示するための**宣言であり、サンドボックスではありません**。プラグインは何でもできます(ファイルの読み書き、シェル実行、ネットワーク、サーバーの設定ファイルの読み取りなど)。自分で読んで信頼できるコードだけを置いてください。Windows のサービス版は LocalSystem(システム権限)で動きます。

## 全体像

- モデルに渡すツールは **組み込みの `web_search`** と **プラグイン**のツールです。
- ツールは **OpenAI 互換のプロバイダー**(`openai-compatible`)の会話でだけ使われます。dsh ブリッジのプロバイダーにはツールを渡しません。
- モデルがツールを呼ぶと、サーバーはまず承認を確認し、承認されたらプラグインの関数を実行して結果をモデルに返します。1 回の応答でツール呼び出しは最大 6 ラウンドまでです。

## 自作の手順(雛形と検査)

作者向けに、雛形の生成と検査のコマンドがあります。`server/` フォルダで実行してください。

```bash
cd server
npm run plugin:new -- my-tool                      # ./my-tool/ に雛形を作る
npm run plugin:new -- my-tool --dir ../plugins     # 別のフォルダに作る
npm run plugin:check -- ./my-tool                  # 検査する
```

- **`plugin:new -- <id> [--dir <outDir>]`**: `<outDir>/<id>/`(既定はカレントフォルダ)に `plugin.json`、`index.mjs`、`README.md` を作ります。例のツールは `<id>` の `-` を `_` に変えて `_hello` を付けた名前です(長い id では名前の基部を切り詰めます)。`id` は `[a-z0-9][a-z0-9_-]{0,39}` の規則に従い、同じ名前のフォルダが既にあれば何もせずに止まります。
- **`plugin:check -- <dir> [--no-run]`**: 次を検査します。
  - `plugin.json` の規則(上の表)。`id` とフォルダ名の一致を含みます。サーバーの読み込みと同じ検査関数を使います。
  - `main` のモジュールが読めて、`tools` の各ツールに関数が export されているか。
  - サイズ(2MB 以内)とファイル数(200 個以内)。
  - `package.json` に `dependencies` / `optionalDependencies` / `peerDependencies` があれば**不可**です。依存パッケージを持つプラグインは導入できないので、1 つのファイルにまとめてください。
  - 各ツールを引数 `{}` で 1 回ずつ実行します。`ctx` には `log`、`signal`、`userId`(`check`)、`config`(`{}`)を渡し、`network` を宣言したツールにだけ `fetch` を渡します。例外は**警告**として表示するだけで、失敗にはしません(必須の引数がないのは普通のことだからです)。副作用のあるツールは `--no-run` で実行を止めてください。
  - 静的スキャン(危ない書き方の目安)は、まだ組み込まれていません。
- 終了コードは、失敗が 1 つでもあれば **1**、なければ **0** です。

`plugin:check` はフォルダを直接見るだけで、サーバーの `$DATA_DIR` は変更しません。検査が通っても、動作の保証にはなりません。実際に使う前に、サーバーを再起動して `GET /tools` で確認してください。

## 管理画面からの導入(GitHub)


管理者は、管理画面の「プラグイン」から GitHub のリポジトリを指定して、プラグインを導入できます。導入できるのは**管理者だけ**です。ZIP のアップロードはありません。

1. **検査**: `owner/name` の形式で GitHub のリポジトリを入力します。任意で、タグ・ブランチ・コミットの指定(ref)と、リポジトリ内のサブフォルダを指定できます。サーバーが GitHub から zip を取得し、**保存せずに**中身を検査します。
2. **警告画面**: 導入の前に、次の内容を必ず表示します。
   - 赤い警告: 「プラグインは、このサーバーの権限で動きます。ファイル、環境変数(API キーを含む)、ネットワークのすべてに触れます。」
   - 取得元のリポジトリと、固定されるコミット SHA。
   - 宣言された権限(`network` など)と、静的スキャンの結果。宣言と食い違うものは強調します。
   - ファイル一覧とサイズ。各ファイルの中身はその場で読めます。
3. **確認**: プラグインの `id` を入力しないと次へ進めません。チェックボックスだけでは導入できません。
4. **導入**: ファイルがプラグインのフォルダに入り、**無効**の状態で登録されます。無効のあいだは、サーバーはプラグインのコードを一切読み込みません。中身を確かめてから、管理者が有効にします。有効にしても、ツールは従来どおり使う設定(Settings → Tools, plugins & search)で有効にする必要があり、`permissions` が空でないツールは呼び出しごとに承認が求められます。
5. **更新**: 自動では更新されません。「更新を確認」で、リポジトリの新しいコミットを取得して差分を見ます。変更されたファイル、増えたツール、増えた権限を見て、もう一度同じ手順で承認します。
6. **削除**: この仕組みで入れたプラグインは、管理画面から削除できます(フォルダ、導入記録、「常に許可」の記録をまとめて消します)。

注意:

- **依存パッケージを持つプラグインは導入できません**(`package.json` に `dependencies` などがある場合)。サーバーは `npm install` を実行しません。
- **静的スキャンは目安で、安全の保証ではありません。** 危ない書き方の一部を見つけるだけです。見つからなくても安全だとは言えません。
- プラグインは**サーバーの OS 権限のまま**動きます。作者を信頼できるものだけを導入してください。
- フォルダを手で置いたプラグイン(一覧では「手元のフォルダ」と表示されます)は、管理画面から無効化も削除もできません。ファイルを直接消してから、再読込してください。

## 置き場所とファイル構成

既定では `$DATA_DIR/plugins/<id>/` に置きます(Docker なら `/data/plugins/<id>/`、Windows サービス版なら `%ProgramData%\OmniChat\data\plugins\<id>\`)。場所は環境変数 `PLUGINS_DIR` で変えられます。

```
$DATA_DIR/plugins/
  my-tool/             ← フォルダ名 = plugin.json の id(必ず一致させる)
    plugin.json        ← マニフェスト(必須)
    index.mjs          ← main で指す ES モジュール
```

- フォルダ名が `.` で始まるものは無視されます。
- プラグインを作ったら、サーバーを再起動するか [読み込みと再読込](#読み込みと再読込) を行ってください。
- **ZIP などのアップロード API はありません**。ファイルを直接置く方式のほかに、管理画面から GitHub のリポジトリを導入する方式があります([管理画面からの導入(GitHub)](#管理画面からの導入github) を参照)。

## plugin.json

```json
{
  "id": "current-time",
  "name": "Current time",
  "version": "1.0.0",
  "description": "Tells the model the current date and time (optionally in an IANA time zone).",
  "main": "index.mjs",
  "tools": [
    {
      "name": "current_time",
      "description": "Get the current date and time. Use it whenever the user asks what time or date it is.",
      "parameters": {
        "type": "object",
        "properties": {
          "timezone": { "type": "string", "description": "Optional IANA time zone, e.g. Asia/Tokyo or UTC." }
        }
      },
      "permissions": []
    }
  ]
}
```

| フィールド | 必須 | 規則 |
|---|---|---|
| `id` | はい | `[a-z0-9][a-z0-9_-]{0,39}`。**フォルダ名と完全に一致**しなければならない |
| `name` | はい | 文字列(表示名) |
| `version` | はい | 文字列 |
| `description` | はい | 文字列 |
| `main` | はい | プラグインフォルダ内の相対パスで `.mjs` または `.js`。`..` を含む、絶対パス、ドライブ文字付きは不可 |
| `tools` | はい | 空でない配列 |
| `tools[].name` | はい | `[a-z0-9_]{1,40}`。**サーバー全体で一意**(組み込みや他のプラグインと同名は不可) |
| `tools[].description` | はい | 文字列。モデルがツールを選ぶ根拠になるので具体的に書く |
| `tools[].parameters` | はい | 引数の JSON Schema(オブジェクト) |
| `tools[].permissions` | 任意 | 次のいずれかの配列。省略は `[]`。`"network"`, `"filesystem-read"`, `"filesystem-write"`, `"shell"` |

マニフェストが不正なプラグインは読み込まれず、`GET /tools` に `available: false` と理由付きで表示されます(他のプラグインには影響しません)。

## モジュールの書き方

`main` で指したモジュールは、ツール名をキーにした関数の入った `tools` を **名前付きで export** します。

```js
// index.mjs
export const tools = {
  async current_time(args, ctx) {
    const now = new Date();
    const zone = args?.timezone || Intl.DateTimeFormat().resolvedOptions().timeZone;
    ctx.log(`current_time ${zone}`);
    return { iso: now.toISOString(), timeZone: zone };
  },
};
```

- `tools` のキーは `plugin.json` の `tools[].name` と一致させます。足りない関数は「module does not export a function for tool …」として、そのツールだけ利用不可になります。
- 関数は `async` でも通常の関数でもかまいません。
- `args` はモデルが組み立てた引数(JSON をパースしたもの)です。**モデルの出力なので、必ず型と範囲を検査してください**。

## ctx(実行時の引数)

| プロパティ | 内容 |
|---|---|
| `ctx.fetch` | `plugin.json` で `"network"` を宣言したツールにだけ渡される `fetch`。宣言していないと `undefined`。別プロセスで動くプラグインでは、サーバーが仲介します(下の[セキュリティ](#セキュリティ)参照) |
| `ctx.signal` | `AbortSignal`。タイムアウトまたは生成の停止で abort される。長い処理は `signal` を見て止めてください |
| `ctx.log(msg)` | サーバーのコンソールに `[tool:<name>] <msg>` として出す(500 文字で切る) |
| `ctx.userId` | 呼び出したユーザーの ID |
| `ctx.config` | 常に `{}`。プラグイン固有の設定の仕組みはまだありません |

`ctx.fetch` は別プロセスのプラグインでは、LAN・ループバック・リンクローカル(クラウドのメタデータ)のアドレスを拒否し、リダイレクトの各先も検査します。サーバー内(手で置いたプラグイン)で動く場合は制限がないので、`fetch_url` の例のとおり URL の検査を自分で行ってください。

## 戻り値・エラー・制限

- **戻り値**: 文字列はそのまま、オブジェクトは `JSON.stringify` して、`undefined` / `null` は空文字としてモデルに返ります。
- **サイズ上限**: 結果は 8 KB を超えると切り詰められ、末尾に `…[truncated]` が付きます。
- **タイムアウト**: 既定 30 秒(`TOOL_TIMEOUT_MS`)。超えると `ctx.signal` が abort され、モデルには `Error: timed out after 30000 ms` が返ります。
- **例外**: `throw new Error("…")` の内容が `Error: …` としてモデルに返り、ツール呼び出しは `error` 状態になります。UI にもその文言が出ます。
- 結果は会話の `toolCalls` に保存され、後の会話には再送されません(最終的なアシスタントの文章だけが履歴に残ります)。

## 権限と承認

`permissions` が空でないツールは、**初回の呼び出しで承認が必要**です。

| 操作 | 結果 |
|---|---|
| **Allow once**(1 回のみ許可) | この 1 回だけ実行。次回も承認を求める |
| **Always allow**(常に許可) | そのユーザーに対して**ツール名ごと**に承認を記録。以後は承認なしで実行される |
| **Deny**(拒否) | 実行しない。モデルには `Error: denied by user` が返る |
| 120 秒無回答 | 拒否扱い(`TOOL_APPROVAL_TIMEOUT_MS` で変更可) |
| 生成の停止、または最後の WebSocket 切断 | 承認待ちは拒否扱い |

補足:

- 承認要求は、そのユーザーの**すべての端末**に届きます。どの端末で回答してもかまいません。
- 承認は引数ごとではなく**ツール名ごと**です。「常に許可」にすると、そのツールは引数に関係なく実行されます。
- 承認の記録は `GET /tool-grants` で確認でき、`DELETE /tool-grants/:tool` で取り消せます(画面は Settings → Tools, plugins & search の中)。
- `permissions: []` のツールは承認を求めません。その分だけ注意してください。
- 承認ダイアログには、ツール名・引数・宣言された権限が表示されます。ダイアログの「This tool can」は宣言された権限の表示です。

**宣言された権限は実際には強制されません。** `filesystem-read` / `filesystem-write` / `shell` と宣言しても、プラグインを止める仕組みはありません。宣言は利用者が判断するための情報です。

## ツールを有効にする

ツールは自動では使われません。次のいずれかで**名前を指定**して有効にします。

- 全体: Settings → Tools, plugins & search(`PUT /settings` の `tools`)
- プロジェクト: プロジェクト設定の Tools
- チャット: チャット設定

解決の順序は **会話 → プロジェクト → 全体** で、会話かプロジェクトに `tools` があれば全体の設定は使われません(`[]` は「なし」)。

有効にしても、承認を省略できるわけではありません。承認の扱いは上の表のとおりです。

## 読み込みと再読込

- サーバー起動時に一度読み込みます。
- 管理者は `POST /tools/reload` で再読込できます(UI の Settings → Tools でも同じ操作があります)。結果は `{tools}` で返ります。
- 再読込では **main のモジュール**を新しく評価し直します。ただし **main から import した別ファイル**は Node のモジュールキャッシュに残るため、変更が反映されないことがあります。そのときはサーバーを再起動してください。単一ファイルにまとめると確実です。
- 読み込みは直列化されており、同時に 2 回走ることはありません。

## サンプル

同梱のサンプルは `server/plugins-examples/` にあります。

| フォルダ | 内容 | 権限 |
|---|---|---|

## トラブルシューティング

| 症状 | 原因と対処 |
|---|---|
| ツールが一覧に出ない | フォルダが `PLUGINS_DIR`(既定 `$DATA_DIR/plugins`)の直下にあるか。フォルダ名が `.` で始まっていないか |
| 一覧に `available: false` で出る | `GET /tools` の `error` を読む。典型は `id must equal the directory name`(フォルダ名と `id` の不一致)、`plugin.json is not valid JSON`、`failed to load index.mjs`(構文エラーや import 失敗) |
| `module does not export a function for tool "x"` | `tools` の中のキーとマニフェストの `name` が一致していない |
| `tool name "x" is already provided by …` | 同名のツールが組み込みか別のプラグインにある。名前を変える |
| 変更が反映されない | 別ファイルを import している場合はサーバー再起動(上の「読み込みと再読込」) |
| モデルがツールを使わない | そのチャットのプロバイダーが `openai-compatible` か、ツールが有効になっているか、モデル自体がツール呼び出しに対応しているか(対応していないモデルでは使われない) |
| 承認が毎回出る | 「常に許可」を選んでいない(または `DELETE /tool-grants/:tool` で取り消された) |
| `Error: timed out after 30000 ms` | 処理が遅い。`TOOL_TIMEOUT_MS` を延ばすか、処理を速くする |
| `network permission is not granted` | `ctx.fetch` を使う関数で `permissions` に `"network"` が無い |

## セキュリティ

### 隔離実行(別プロセス)

環境変数 `PLUGIN_ISOLATION` で決めます。

| 値 | 動き |
|---|---|
| 未設定 / `process`(既定) | 管理画面から導入したプラグイン(`plugin_installs` の行があるもの)は別プロセス。手で置いたフォルダのプラグインはサーバー内 |
| `inproc` | すべてサーバー内(段階 1 と同じ。互換・調査用) |
| `process-all` | 手で置いたものも含め、すべて別プロセス |

別プロセスは Node の `--permission` で起動し、次を強制します(Node 24 で実測、[PLUGIN-INSTALL.md](design/PLUGIN-INSTALL.md) §5)。

- **ファイルの読み取り**: プラグインのフォルダと、子プロセスの起動用ファイルだけ。外側のファイルは `ERR_ACCESS_DENIED`。
- **ファイルの書き込み**: 一切許可しない(プラグインのフォルダへの書き込みも不可)。
- **子プロセス・ワーカースレッド・ネイティブアドオン**: 禁止。
- **環境変数**: サーバーの環境変数は渡さない(子は空の環境で起動する。Windows では OS が必要とする既定の変数だけが入る)。
- **メモリ**: `PLUGIN_MEMORY_MB`(既定 256)を上限にする。
- **時間**: 呼び出しごとの `TOOL_TIMEOUT_MS`。超えると子を止める。停止・再読込・無効化・削除・サーバー終了でも止まる。`PLUGIN_IDLE_MINUTES`(既定 5)使われないと止まり、次の呼び出しで起動し直す。

**強制されないこと(重要)**: この Node 版では、**ネットワークは `--permission` で止まりません**。`net`、`http`、`fetch`、`dns` を直接使うプラグインは、宣言がなくても外へ接続できます。そのため次の対策は、正しく書かれたプラグインを閉じ込めるための仲介であり、悪意あるプラグインへの保証ではありません。

- `ctx.fetch` は親が仲介します。http / https だけ、DNS を解決して **いずれかのアドレスが拒否対象なら止める**、接続先を検査済みのアドレスに固定する、リダイレクトの各先を検査する、応答は 2 MB まで、15 秒まで。拒否対象は、ループバック、プライベート LAN(10/8、172.16/12、192.168/16)、リンクローカル(169.254/16、クラウドのメタデータを含む)、CGNAT、マルチキャスト、IPv6 の同等の範囲(fc00::/7、fe80::/10、::ffff: の埋め込みを含む)です。
- 直接の通信を止めるには、OS やネットワークの層(ファイアウォール、コンテナ)で行う必要があります。

**プラグインの作者を信頼しないなら、このサーバーに置かないでください。** 隔離は「宣言どおりに動くプラグイン」の事故を減らすためのもので、「悪意あるコード」への防御としては不十分です。

- プラグインは OmniChat のアカウントを持つ人が**間接的に**使える機能になります。モデルが承認を経て呼び出すため、承認の「常に許可」は慎重に選んでください。
- 手で置いたプラグインはサーバーの OS 権限で動くので、ファイルシステム全体、環境変数(トークンを含むものを含む)、ネットワークに到達できます。管理画面から導入したものは別プロセスで動き、ファイルと環境変数は制限されますが、ネットワークは止められません(上の「強制されないこと」)。
- ネットワーク系ツールは、サーバーから見える LAN やローカルのサービスにも届きます。
- 管理画面からは、GitHub のリポジトリを指定して導入します(コードのアップロードはできません)。手で置く場合は、サーバー PC への直接のファイル操作になります。サーバーの管理は、その PC の管理と同じ扱いにしてください。
- 検索(`web_search`)の詳細と注意は [SEARCH.md](SEARCH.md) を参照してください。
