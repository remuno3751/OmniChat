# 設計: プラグインの自作・読み込み・他者配布プラグインの導入

状態: **提案(決めてほしい点あり)**。2026-10-19。

## 今あるもの([docs/PLUGINS.md](../PLUGINS.md))
- ツール(モデルが呼ぶ関数)を `$DATA_DIR/plugins/<id>/`(`plugin.json` + `index.mjs`)に置く。サーバー起動時と `POST /tools/reload` で読み込む。
- `permissions`(`network` / `filesystem-read` / `filesystem-write` / `shell`)は**宣言だけで強制されない**。初回の呼び出しで承認ダイアログが出る。
- **プラグインはサーバーのプロセス内で、サーバーの OS 権限のまま動く**(環境変数のトークン、ファイル、ネットワークすべてに届く)。アップロード API はない(ファイルを直接置く)。
- 足りないもの: 作りやすさ(雛形、検証)、画面からの導入、配布元からの取得、導入時のセキュリティ警告、更新・削除、権限の強制。

## 方針
**導入できるのは管理者だけ**(プラグインはサーバーの権限で動くので、一般ユーザーには許さない)。導入は常に「確認画面 → 明示的な承認 → **無効の状態で**入る → 管理者がツールごとに有効化」の順。

### 1. 自作
- `npm run plugin:new -- <id>`(または管理画面の「雛形を作る」)で、`plugin.json` + `index.mjs` + `README` を生成する。
- `npm run plugin:check -- <dir>`: マニフェストの検査(既存の読み込みと同じ規則)、export の一致、サイズ、静的スキャン(下記)、サンプル引数での試行実行。
- 作者向けの文書は PLUGINS.md を整理して「自作」の章を足す。

### 2. 読み込み(ローカル)
- 管理画面「プラグイン」: 一覧(id、版、出どころ、ツール、宣言された権限、有効 / 無効、読み込みエラー)、再読込、削除。
- フォルダを置く従来の方法はそのまま使える(出どころ = 「手元のフォルダ」)。
- ZIP のアップロード(管理者のみ。上限 5MB、ファイル数 200)も同じ導入の流れに乗せる。

### 3. 他者の配布(GitHub など)
- 入力: `https://github.com/<owner>/<repo>`(任意で `@<タグ / ブランチ / コミット>`、サブフォルダ指定)。**最初の対応は GitHub のみ**(zipball を取得)。任意の URL は対象外(下の決定事項)。
- 取得は**サーバーが GitHub から zip をダウンロード**し、展開せずに検査する(`jszip` は導入済み)。パスの検査(`..`、絶対パス、シンボリックリンク)、サイズ・ファイル数の上限。`.git`、`node_modules` は含めない。**依存パッケージが要るプラグインは対象外**(`package.json` の `dependencies` があれば導入を断る。ビルド済みの単一ファイルにしてもらう)。`npm install` や任意のスクリプトは**一切実行しない**。
- **コミット SHA に固定**して記録する(タグやブランチが後から書き換わっても、勝手に変わらない)。ファイルごとの SHA-256 も記録する。
- 更新: **自動更新しない**。「更新を確認」で新しい版を取得し、**変更されたファイルの差分**と、権限・ツールの増減を見せて、再び承認を求める。

### 4. 導入時のセキュリティ警告(確認画面)
導入前に必ず出す。ここで「次へ」を押すまで、ファイルはプラグインのフォルダに置かない。
1. **赤い警告**: 「プラグインは、このサーバーの権限で動きます。ファイル、環境変数(API キーを含む)、ネットワークのすべてに触れます。作者を信頼できないコードは入れないでください。」
2. 出どころ: リポジトリ、コミット SHA、作者、星の数などは出さない(信頼の目安にならない)。**取得元の URL とコミット SHA だけ**を事実として出す。
3. 宣言された権限と、**コードの静的スキャンの結果**(宣言と食い違う場合は強調): `child_process`、`fs` の書き込み、`process.env`、`eval` / `new Function`、動的 `import`、`net` / `http` の直接利用、難読化の疑い(長い 1 行、`\x` の連続)。スキャンは**目安であり、安全の保証ではない**と明記する。
4. ファイル一覧とサイズ、各ファイルの中身を、その場で読める(ソース表示)。
5. 承認の方法: プラグインの `id` を**入力させる**(「確認した」のチェックボックスだけにしない)。管理者のパスワードの再入力を求める案もある(下の決定事項)。
6. 導入後は**無効**。ツールごとに管理者が有効にする。ツールを有効にしても、`permissions` が空でないツールは、従来どおり利用者が呼び出しごとに(または「常に許可」で)承認する。

### 5. 強制(サンドボックス)
- **段階 1(警告のみ)**: 上記のとおり。今の実行方式(サーバーのプロセス内)のまま。PLUGINS.md の警告と一致している。
- **段階 2(隔離実行)**: プラグインを**別プロセス**(Node の `--permission` モデルで、ファイルの読み取りをプラグインのフォルダだけに限定し、子プロセスと Worker、ネイティブアドオンを禁止)で動かし、ネットワークは `network` を宣言したプラグインにだけ、**親が仲介する `ctx.fetch`**(LAN / localhost / メタデータアドレスを既定で拒否)を渡す。サーバーの環境変数は渡さない。ツールの呼び出しは IPC(JSON)で行う。これで、宣言が**実際に強制**される。
  - 注意(**実測済み**、下の「実測結果」): Node 24 の `--permission` は**ネットワークを止めない**。したがって段階 2 は、ネットワークを「親が仲介する `ctx.fetch`」で抑えるに留まる。直接の通信は止められず、UI と docs にそう書く。
  - 段階 2 は工数が大きい(別プロセスの管理、IPC、タイムアウト、再起動)。段階 1 を先に出し、他者配布のプラグインは、段階 2 ができるまで「警告つきで導入可」とする案と、「段階 2 ができるまで導入不可」とする案がある(下の決定事項)。
  - **状況(実装済み)**: `server/src/plugin-sandbox.ts`(親側: 子の管理、IPC、`ctx.fetch` の仲介)と `server/src/plugin-host.mjs`(子の入口)。管理画面から導入したプラグインは既定で隔離、手で置いたものは従来どおりサーバー内。`PLUGIN_ISOLATION`(`process` 既定 / `inproc` / `process-all`)で切り替える。使い方と限界は [PLUGINS.md](../PLUGINS.md) のセキュリティの章。テストは `server/src/plugin-sandbox.test.ts`。
  - 子の起動は遅延(最初の呼び出しで起動、アイドル 5 分で停止、停止・再読込・無効化・削除・サーバー終了で停止、クラッシュ・タイムアウトの後は次の呼び出しで再起動)。
  - API は変えない(`plugin.json`、`export const tools`、ctx、8 KB 上限、タイムアウト、承認の流れ)。`GET /tools` のプラグインには `isolation` が付く(追加のみ)。
  - 既知の差: 隔離されたプラグインは、`filesystem-write` を宣言していても書き込めない。モジュールの読み込みは最初の呼び出しまで行われないため、ツールの `available` は読み込み失敗を事前には出せず、呼び出し時にエラーになる(`plugin.json` の `main` の存在だけは事前に確認する)。

#### 実測結果(段階 2、Node 24.19.0、Windows 11)

テスト用のプラグインが次を試した結果。「素の起動」は権限の指定なし。子は `--permission --allow-fs-read=<子の入口ファイル> --allow-fs-read=<プラグインのフォルダ>/*` で起動。

| 項目 | 素の起動 | `--permission`(上の指定) | 結論 |
|---|---|---|---|
| (1) 読み取り: プラグインのフォルダ外 | 許可 | **拒否** `ERR_ACCESS_DENIED` | 強制される |
| (1') 読み取り: プラグインのフォルダ内 | 許可 | 許可 | 期待どおり |
| (2) 書き込み(フォルダの内・外とも) | 許可 | **拒否** `ERR_ACCESS_DENIED` | 強制される(書き込みの許可は、今は一切付けない) |
| (3) `child_process`(spawnSync / execSync) | 許可 | **拒否** `ERR_ACCESS_DENIED` | 強制される |
| (4) ネットワーク: `net.connect`、`http.get`、`fetch`(ループバックと公開の https)、`dns.lookup` | 許可 | **すべて許可** | **強制されない**。DNS も止まらない |
| ワーカースレッド | 許可 | 拒否 `ERR_ACCESS_DENIED`(`--allow-worker` なし) | 強制される |
| ネイティブアドオン(`process.dlopen`) | 失敗(存在しないファイル) | 拒否 `ERR_DLOPEN_DISABLED` | 強制される |
| (5) 環境変数: 親の環境変数(canary)を子に渡す | 見える | `spawn` の `env: {}` で子を起動すると**見えない** | 強制される。ただし Windows では `env: {}` でも OS の既定変数(PATH、SYSTEMROOT、TEMP、USERPROFILE など 11 個)が入る |

- 読み取りの許可は、子の入口ファイルは**そのファイルだけ**、プラグインのフォルダは**フォルダの中身**(`/*`)で足りた。
- 結論: `--permission` が守るのは「ファイル・子プロセス・ワーカー・アドオン・環境変数」。**ネットワークは守れない**。これは Node 24.19 の仕様で、回避する手段は別のプロセス設定(OS のファイアウォール、コンテナ)になる。
- 対策(実装): `ctx.fetch` を親が仲介する。拒否対象は、ループバック、プライベート LAN、リンクローカル(メタデータを含む)、CGNAT、マルチキャスト、IPv6 の同等の範囲。DNS の全アドレスを検査し、検査したアドレスに接続を固定する。リダイレクトの各先を検査する。http / https だけ。応答 2 MB、15 秒まで。
- テストの特別な扱い: `PLUGIN_FETCH_ALLOW_PRIVATE=1` はテスト専用で、**ループバックだけ**を通す(LAN とメタデータは、このフラグでも拒否のまま)。本番では設定しない。

### 6. データ
- 表 `plugin_installs (id TEXT PRIMARY KEY, source TEXT /* local|github|zip */, repo TEXT, ref TEXT, commit_sha TEXT, files_sha256 TEXT /* JSON */, installed_by TEXT, installed_at INTEGER, enabled INTEGER, scan_json TEXT)`。導入の履歴(誰がいつ、どのコミットを入れたか)を残す。
- 管理者の導入・有効化・削除は監査ログに残す(既存の仕組みがあれば使う)。
- バックアップには、プラグインのフォルダを含める(DB と同じ扱い)。

### 7. API(案)
- `POST /admin/plugins/inspect`: `{ source: "github", repo, ref? }` または ZIP → ダウンロードして検査し、`{ inspectionId, manifest, files, scan, warnings }` を返す(まだ入れない)。
- `POST /admin/plugins/install`: `{ inspectionId, confirmId }`(`confirmId` はプラグインの id と一致が必要)→ 無効で導入。
- `GET /admin/plugins`、`PATCH /admin/plugins/:id`(有効 / 無効)、`DELETE /admin/plugins/:id`、`POST /admin/plugins/:id/check-update`。
- すべて管理者のみ。メンテナンスモード中も可。

### 8. クライアント / サーバーアプリ
- クライアントの管理画面と OmniChat Server アプリに「プラグイン」画面(一覧、導入の流れ、確認画面、更新、削除)。

## 工数の目安
- 自作の雛形と検査コマンド、文書: 0.5〜1 日
- 導入の流れ(GitHub 取得、検査、静的スキャン、API、DB): 2〜3 日
- 管理画面(クライアント + サーバーアプリ): 1.5 日
- 段階 2 の隔離実行: 3〜5 日(Node の版による制約の調査を含む)

## 決めてほしい点(推奨を先頭に)
1. **誰が導入できるか**: 管理者のみ(推奨) / 一般ユーザーも自分用に(サーバーの権限で動くので非推奨)。
2. **取得元**: GitHub のみ(推奨) / 任意の URL も / ZIP のアップロードも。
3. **他者配布のプラグインの扱い**: 警告つきで導入可(段階 1 から。推奨) / 隔離実行(段階 2)ができるまで導入不可。
4. **導入時の確認**: プラグインの id を入力 + 警告(推奨) / さらに管理者のパスワード再入力。
5. **依存パッケージ**: 持つプラグインは断る(推奨。単一ファイルにしてもらう) / `npm install` を許す(任意コードの実行になるため非推奨)。
