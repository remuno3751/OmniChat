# OmniChat v4: Chat/Code split, phases, Code operations, Pets (extends PROTOCOL-v3 and phases 2-5)

Source: spec "Chat/Code分離・導入・Pets" (2026-10-17). This file is the contract for the NIGHT work (foundations). Night UI may be minimal; real UI polish is the next day.

Resolved open questions:
- **Codex Pets format** (read from `~/.codex/pets/mintcodexpet` and the hatch-pet skill): a pet is a folder with `pet.json` `{id, displayName, description, spriteVersionNumber: 1|2, spritesheetPath}` and a transparent PNG/WebP spritesheet. v2 = 8 columns x 11 rows, cell 192x208 (1536x2288); v1 = 8x9 (1536x1872). Rows: 0 idle(6 frames: 280,110,110,140,140,320 ms) · 1 running-right(8: 120ms, last 220) · 2 running-left(8) · 3 waving(4: 140, last 280) · 4 jumping(5: 140, last 280) · 5 failed(8: 140, last 240) · 6 waiting(6: 150, last 260) · 7 running(6: 120, last 220) · 8 review(6: 150, last 280) · v2 only: rows 9-10 = 16 clockwise look directions (000=up,022.5,...,337.5; 8 per row; 000 is NOT neutral). Unused cells are transparent. Rights: do NOT bundle anybody's pet; users import their own (the existing Mint pet is the user's).
- **DHS events usable** (from DSH-PLUGIN-RESEARCH.md): `session/event` types `turn/start|end`, `step/start|end`, `user/message`, `assistant/message`, `tool/call{callId,name,arguments}`, `tool/result`, `approval/asked|decided`, `approval/request` (waterfall, can be intercepted), `session/title`, `model/selection`. Diffs are NOT an event: derive them from `git diff` in the session cwd (and from `tool/call` arguments of edit/write tools). Sub-agents: not yet researched; the bridge reports them when it can see them (`agents` service / events), otherwise the list stays empty.
- Approval operations in the app: allow once / always (as a rule) / deny only. No editing of the command.

## 1. Chat / Code mode
- `conversations.mode TEXT NOT NULL DEFAULT 'chat'` (`'chat' | 'code'`) and the same on `projects`. A conversation whose provider kind is `dsh-bridge` is created with `mode: 'code'` by default; the app may set it explicitly. `Conversation.mode`, `Project.mode` in all API/sync payloads; `PUT /conversations/:id` and `PUT /projects/:id` accept `mode`. Lists are filtered client-side (the server returns all).
- `Conversation.codeStatus: 'idle'|'running'|'awaiting_approval'|'done'|'error'` (derived and stored on every state change; synced like other fields). Set by the server for chat runs (running while generating, done/error at the end) and by the bridge path for Code runs.
- `GET /code/sessions` -> `{sessions: [{conversationId, title, projectId, cwd, bridge, codeStatus, updatedAt, pendingApprovals: number}]}` for the user's code-mode conversations (non-deleted), newest first. Parallel runs are simply several running conversations (one run per conversation).

## 2. Phase events (staged status)
- WS server->client `{type:"phase", conversationId, messageId, phase: "thinking"|"searching"|"tool"|"subagent"|"answering", state: "start"|"end", label?: string, at: number /*ms*/, id?: string}`. `id` pairs a start with its end (default: the phase name). `label` is a short human text in the server language `en` (the app maps known phases through i18n; unknown labels are shown as-is).
- The harness (server `chat.ts`; bridge for dsh) emits them; models never write the preface themselves:
  - `thinking` start at the first reasoning delta, end at the first text delta/tool call;
  - `searching` start/end around `injectSearch`/the `web_search` tool (label = query); quotes fetching counts as `searching` (label "market quote");
  - `tool` start/end around every tool call (label = tool name); `subagent` from the bridge; `answering` start at the first text delta, end at completion.
- Persisted on the message as `phases: [{id, phase, label?, start, end|null}]` (capped 100) so a reload/other device shows the folded history. Included in upsert/sync/snapshot. Terminal states (`done|error|stopped`) close any open phase.

## 3. Code operations data (bridge -> server -> clients)
- Message fields (assistant message of a Code run), synced: `changes: [{path, status: "added"|"modified"|"deleted"|"renamed", additions, deletions, patch?: string /*unified diff, per file capped 200 KB, total 1 MB*/}]` and `agents: [{id, role, status: "running"|"done"|"error", startedAt, endedAt|null, summary?: string, log?: string /*capped 64 KB*/}]`. `GET /messages/:id/changes` returns the full `patch` texts; the synced message carries only `{path,status,additions,deletions}` + `patch` omitted when larger than 20 KB.
- Bridge->server frames (extend BRIDGE-v2): `{type:"changes", requestId, changes:[...]}` at the end of a run (bridge computes `git diff --numstat` + per-file patch against the checkpoint taken before the run; non-git cwd -> empty + `warning: "not a git repository"` in the run's `done` frame); `{type:"agents", requestId, agents:[...]}` whenever the list changes.
- Tool/command history: existing `toolCalls` on the message (time-ordered, collapsible in the UI); the bridge fills them from `tool/call` + `tool/result`.

## 4. Approval rules
- Table `approval_rules(id TEXT PK, user_id, project_id TEXT NULL, kind TEXT /*'tool'|'command'|'path'*/, pattern TEXT /*exact tool name, or glob over the command line / path*/, action TEXT /*'allow'|'deny'|'ask'*/, created_at, note)`. REST: `GET /approval-rules?projectId=`, `PUT /approval-rules/:id`, `DELETE /approval-rules/:id` (auth, owner only, pattern <= 300 chars, <= 500 rules/user).
- Evaluation (server `tools/approvals.ts`, also used for bridge approvals): most specific wins — project rule over global, `deny` over `allow` over `ask`; no match -> `ask` (default is safe). A matching `allow`/`deny` answers immediately without a prompt; the tool call/approval record notes `decidedBy: "rule:<id>"`. "Always allow" in the approval dialog creates an `allow` rule (tool kind) instead of only a grant (existing grants keep working and are shown as rules).
- Bridge/dsh approvals: bridge->server frame `{type:"approval", requestId, approvalId, tool, command?, path?, reason?}`; server answers with `{type:"approval_reply", approvalId, decision:"allowed-once"|"rejected"}` after rules/user. Forwarded to clients as the existing `tool_approval` WS message (+ `conversationId`, `codeStatus: awaiting_approval`).

## 5. Notifications
- Settings (synced): `notify: {done: boolean, approval: boolean, error: boolean}` (default all true) and `notifyUrl: string|null` (an ntfy-compatible topic URL, e.g. `https://ntfy.sh/<topic>`; server POSTs the text body with `Title`, `Priority`, `Tags` headers; this is the Android/Windows push path without Firebase; the URL is never echoed back in full: GET /settings returns `notifyUrlSet: boolean`).
- WS server->client `{type:"notify", kind:"done"|"approval"|"error", conversationId, title, body, at}` broadcast to the user's devices on: a Code (or chat) run finishing, an approval becoming pending, an error. Clients show an OS notification (Notification API on web/desktop; the same event drives Pets). Server also POSTs to `notifyUrl` when the kind is enabled. `POST /notify/test` sends a test to the configured URL (admin or owner).

## 6. Checkpoints and rewind (Code)
- Bridge, before each run in a git working tree: snapshot the tree WITHOUT touching the user's branch/index: temp `GIT_INDEX_FILE`, `git add -A`, `git write-tree`, `git commit-tree -m "omnichat checkpoint <id>"`, store as ref `refs/omnichat/checkpoints/<id>`. Frame `{type:"checkpoint", requestId, checkpointId, ref, createdAt, dirty: boolean}`; the server stores `checkpoints(id, user_id, conversation_id, message_id, bridge, cwd, ref, created_at)`. Non-git cwd: frame `{type:"checkpoint", ..., unavailable:"not a git repository"}`; clients show a warning.
- `GET /code/checkpoints?conversationId=`; `POST /code/checkpoints/:id/rewind` -> server sends `{type:"rewind", requestId, ref, cwd}`; bridge restores tracked and added files from the snapshot (read-tree into a temp index + `checkout-index -a -f`, deleting files that did not exist at the checkpoint only when `{removeNew:true}` is passed) and replies `{type:"rewound", requestId, ok, error?}`. Always requires an explicit client confirmation (the app's job); the server refuses while the conversation is `running`.

## 7. Diagnostics
- `GET /admin/diagnostics` (admin) -> `text/markdown`: server version, node version, uptime, platform, port/host, data dir and size, DB size, user/device counts (no names), providers (name, kind, host only, reachable yes/no, model count), search backend status, connected bridges (names), config summary (booleans/limits only), last 40 log lines. Secrets (tokens, API keys, passwords, notifyUrl, full URLs with credentials) are masked as `***`. The server keeps an in-memory ring buffer of the last 200 log lines.
- CLI: `omnichat doctor [--server URL]` prints the same Markdown (also works offline: reports "server unreachable" with the checks it can do: node version, port in use, data dir writable, config file found). Exit code 0 if all checks pass, 1 otherwise.

## 8. Templates and slash commands
- Table `templates(id, user_id, project_id NULL, name, body, description, kind /*'prompt'|'action'*/, created_at, updated_at, deleted)`; `kind:'action'` bodies are one of `new_session`, `approval_mode:<ask|rules>`, `search:<off|smart|auto|always>`. Variables in `body`: `{{name}}` (the app prompts for them before sending). REST `GET /templates?projectId=`, `PUT /templates/:id`, `DELETE /templates/:id`; synced via `GET /sync` like projects (add to `/sync`, snapshot and WS upsert: `templates` array). Names unique per scope, <= 60 chars; body <= 20 000.

## 9. Pets
- Server stores a user's imported pets so every device has them: `pets(id, user_id, name, manifest JSON, sheet BLOB, mime, created_at)`; `POST /pets` `{manifest:{id,displayName,description,spriteVersionNumber,spritesheetPath}, sheetBase64, mime:"image/png"|"image/webp"}` (<= 8 MB decoded; validates the manifest and, for PNG/WebP, the pixel size 1536x2288 (v2) or 1536x1872 (v1) by reading the header), `GET /pets` (list without blobs), `GET /pets/:id/sheet` (binary), `DELETE /pets/:id`. The app loads a Codex pet by picking a folder / `pet.json` + spritesheet (or a zip) and uploads it.
- Settings (per device, NOT synced): `pets: {enabled, petId, size, activity: "low"|"normal"|"high", clickThrough: true}`; `activePetId` synced is optional. State -> row mapping (client): idle=0; thinking/tool/subagent/answering/running=7 (running); searching=8 (review); awaiting approval/`notify:approval`=6 (waiting); error=5 (failed); done/`notify:done`=4 (jumping) then 3 (waving) once; walking uses rows 1/2; v2 look rows follow the pointer. Reduced motion / low power / phones: show frame 0 of idle or lower the frame rate.

## 10. Settings structure, i18n, appearance (app)
- Language files `app/src/i18n/ja.ts`, `en.ts` (flat keys, `{name}` placeholders) + `t(key, vars)` hook and a registry so more languages are one file. Language is per device (default from the browser/OS).
- Settings split into pages: General / Appearance / Models / Chat / Code / Plugins / Connections / Developer. Each setting is declared as `scope: "device" | "synced"` in one table (`app/src/settingsMeta.ts`); device settings live in local storage (language, theme, font size, message width, code highlight scheme, pets), synced ones in `/settings`.
- Appearance: light/dark + extra themes (>= 2: e.g. "sepia", "high contrast"), code highlight scheme (>= 3), font size, message width.

## 11. Install and AI manual (docs, packaging, CLI)
- `docs/AI-INSTALL.md`: a manual an AI coding agent can follow: prerequisites, exact commands (Windows PowerShell and Linux/macOS), a table of every setting/env var, each step with a "How to verify success" (exact command + expected output) and a retry rule, "Troubleshooting" that starts with `omnichat doctor` / `GET /admin/diagnostics`. `docs/QUICKSTART.md`: one page for humans. Server installers (Windows `packaging/windows`, Linux systemd, macOS launchd, Docker) get a unified `install-server` script per OS that checks dependencies (Node >= 24), writes a config file (port, auth/registration policy, SEARXNG_URL, DHS bridge name), registers the service and runs the doctor. Client installers stay as in the earlier spec (APK, desktop).
