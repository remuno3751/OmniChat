# OmniChat v3 phase 4: developer features (extends PROTOCOL-v3.md, -phase2, -phase3)

Spec "開発者向け機能" (all behind the existing developer-mode toggle in the UI): model comparison, benchmark runner, structured output, token view, config as files, CLI. NOT in scope: chat-template editing (no backend exposes a safe, portable way; the final prompt viewer already shows what was sent) — say so in the docs.

## 1. Structured output, extra body, logprobs
- `ResponseFormat = {type:"json_object"} | {type:"json_schema", name?: string, schema: object}`.
- `Conversation` gains `responseFormat: ResponseFormat | null`; WS `send`/`regenerate`/`compare` accept a one-shot `responseFormat`; `/v1/chat/completions` already forwards `response_format`. Resolution: one-shot > conversation > null. Sent to openai-compatible backends as OpenAI `response_format` (`json_schema` form: `{type:"json_schema", json_schema:{name, schema, strict:true}}`). dsh-bridge ignores it.
- After completion, if a responseFormat was used the server runs `JSON.parse` on the content and (for json_schema) a minimal schema check (type/required/properties types/enum; no external validator dependency unless one is already installed) and records `jsonValid: boolean` and `jsonError?: string` in `message.metrics` extras → `Metrics` gains `jsonValid?: boolean | null`.
- `SamplingParams` gains `logprobs?: number | null` (top-N, 0..20), `grammar?: string | null` (llama.cpp GBNF passthrough as body field `grammar`) and `extraBody?: object | null` (merged into the request body AFTER everything else but may never override `model`, `messages`, `stream`, `tools`, `stream_options`, `response_format`). All three follow the usual merge layers (extraBody shallow-merged key by key). `logprobs` is sent as `logprobs:true, top_logprobs:N`; the returned logprobs are stored (capped 256 KB) in the debug record `response.logprobs` and NOT in the message.

## 2. Token view
`POST /tokenize {providerId?, model?, text}` -> `{tokens:[{id?: number, text: string}], count: number, exact: boolean, source: "llama.cpp" | "estimate"}`. llama.cpp backends: `POST {origin}/tokenize {content, add_special:false, with_pieces:true}` (fallback: tokenize + `/detokenize` per token); everything else: estimated pseudo-tokens (the same estimator as tokens.ts, split into pieces by the CJK-aware rule), `exact:false`. Cap text at 20 000 chars. Also `GET /messages/:id/debug` `response.logprobs` carries per-token logprobs when requested.

## 3. Model comparison (stateless, saved separately from chats)
- WS client->server `{type:"compare", compareId, prompt, systemPrompt?: string|null, targets:[{providerId, model, effort?, params?, responseFormat?}] (1..4), sequential?: boolean (default true)}`; server->client `{type:"compare_delta", compareId, index, kind:"text"|"reasoning", text}` and `{type:"compare_done", compareId, index, status:"done"|"error"|"stopped", content, reasoning, metrics, error?}` and a final `{type:"compare_complete", compareId}`. `{type:"compare_stop", compareId}` stops all. Default sequential execution because parallel runs on one local GPU distort speed; `sequential:false` runs concurrently. Uses the same provider layer, params/effort resolution (one-shot only: no conversation context), metrics collection and `AbortController` handling as chat; dsh-bridge targets are rejected (`error`). Not written to chat history and not counted in /stats (flag `source:"compare"`).
- Persistence: table `comparisons(id, user_id, created_at, prompt, system_prompt, targets JSON, results JSON)`; `GET /comparisons` (list, newest first, light), `GET /comparisons/:id`, `DELETE /comparisons/:id`; synced? no (fetched on demand).

## 4. Benchmark runner
- Prompt sets: `PUT /bench/sets/:id {name, prompts: string[] (1..50, each <= 8000 chars), systemPrompt?: string|null}`, `GET /bench/sets`, `DELETE /bench/sets/:id`.
- Runs: `POST /bench/runs {setId, targets:[{providerId, model, effort?, params?}] (1..6), repeats?: 1..5 (default 1), warmup?: boolean (default true: one discarded tiny request per target to load the model), maxTokens?: number (default 256)}` -> `{runId}`; executes asynchronously on the server, strictly sequential (one run at a time per user; a second POST returns 409), each (target × prompt × repeat) as an isolated non-stored generation; progress WS `{type:"bench_progress", runId, done, total, current?}` and `{type:"bench_done", runId, status}`; `POST /bench/runs/:id/cancel`; survives client disconnects; a server restart marks running runs `error`.
- Results: `GET /bench/runs` (list), `GET /bench/runs/:id` -> `{id, setId, setName, status, startedAt, finishedAt, targets, repeats, results:[{targetIndex, promptIndex, repeat, status, ttftMs, prefillTps, decodeTps, completionTokens, reasoningTokens, totalMs, source, error?}], summary:[{targetIndex, providerName, model, quantization, contextLength, n, avgTtftMs, avgPrefillTps, avgDecodeTps, p50DecodeTps, minDecodeTps, maxDecodeTps, errors, estimatedShare}]}`, `GET /bench/runs/:id/export` (CSV), `DELETE /bench/runs/:id`. Content of the answers is stored truncated (first 500 chars) per result for sanity checks.

## 5. Config as files
`GET /config/export?format=json|yaml` -> portable config `{version:1, exportedAt, settings:{systemPrompt, effort, params, modelParams, tools, searchMode, autoTitle, titleModel, contextOverflow, contextLimits}, projects:[{name, systemPrompt, systemMode, defaultModel /*"providerName::model"*/, effort, params, tools, searchMode}], presets:[{name, text}], benchSets:[{name, prompts, systemPrompt}]}` — references providers by NAME not id, contains no secrets, no conversations. `POST /config/import {format, content, mode:"merge"|"replace"?}` (content = string of JSON/YAML; default merge): projects/presets/benchSets matched by name (update if exists, else create), settings merged; returns `{created:{...}, updated:{...}, skipped:[...reasons]}`; validation like the PUT endpoints; 1 MB limit. YAML via the `yaml` package (add as a server dependency).

## 6. CLI (`cli/`, zero runtime dependencies, Node >= 22)
Command `omnichat` (bin in cli/package.json): `login --server URL [--username U]` (password from prompt without echo or `OMNICHAT_PASSWORD`; stores `{server, token, deviceId}` in `~/.config/omnichat/config.json` with file mode 0600 where supported; creates a device named "CLI (<hostname>)"), `logout`, `whoami`, `models [--provider]`, `chat "<message>" [--model <providerName>/<id>] [--project <name>] [--conv <id>|--new] [--effort low|medium|high|max] [--search off|auto|always] [--system "<text>"] [--json]` (streams the answer to stdout over the WS, reads the message from stdin when `-` or when piped, prints thinking to stderr only with `--thinking`, tool approvals: `--approve once|always|deny` default deny non-interactively and asks on a TTY), `history [--limit N] [--project name]`, `show <conversationId>` (path of the current branch as text), `search "<q>"` (GET /history/search), `export <conversationId> [--format md|json] [-o file]`, `bench run <setName> --targets "<prov>/<model>,..." [--repeats N]` (prints the summary table), `config export|import [file]`. Exit codes: 0 ok, 1 error, 2 usage. `--server`/`OMNICHAT_SERVER` and `OMNICHAT_TOKEN` override the config file. README in Japanese; unit tests with node:test and a fake server.

## 8. Server implementation notes (server C) - deviations and details
- Compare: a `dsh-bridge` target (or any non-openai-compatible provider) is refused up front with one `{type:"error", compareId}` frame and nothing runs. A top-level `responseFormat` on the `compare` frame is the default for targets without their own. Targets that were not reached (stop) are stored with `status:"stopped"`. `compare_done` also carries `reasoning`. Metrics carry `origin:"compare"` and are never written to `metrics`, so `/stats` does not count them.
- Compare/benchmark run stateless generations: no conversation context, no tools, no search, no approvals. Resolution is one-shot > `settings.modelParams[<providerId>::<model>]` > global (project and conversation layers do not apply).
- Benchmark: warm-up is one request per target (`max_tokens` 8, prompt "Hi"), not stored, and runs before the first prompt of that target. Result rows also carry `answer` (first 500 characters), `quantization` and `contextLength`; the summary carries `quantization` and `contextLength` too. A provider deleted mid-run turns its remaining items into `error` rows. `bench_progress` / `bench_done` are broadcast to all devices of the user. `DELETE /bench/runs/:id` of a running run returns 409. Runs whose targets are not openai-compatible are refused with 400 at start.
- `POST /tokenize`: text over 20 000 characters is truncated (response `truncated:true`), not refused. llama.cpp builds that answer `/tokenize` with ids only are detokenized per token (bounded to 4 000 tokens; above that the pieces are empty strings). A provider that is not llama.cpp, or no provider, gives the estimate (`exact:false`).
- Structured output: `responseFormat` is sent only to openai-compatible backends; `json_object` also requires a top-level object. The schema check is minimal (type, enum, const, required, properties, items, min/max length, items, numeric bounds, `additionalProperties:false`); there is no external validator. Metrics carry `jsonValid`/`jsonError` only when a response format was in effect for the reply.
- Logprobs: stored in the debug record `response.logprobs` (`{content:[...], truncated?}`), capped at 256 KB, outside the normal debug cap. `extraBody` is capped at 32 KB, `grammar` at 100 000 characters. Unknown `extraBody` keys are passed through; `model`, `messages`, `stream`, `tools`, `stream_options` and `response_format` are silently dropped from it.
- Config export/import: providers are referenced as `"<providerName>::<model>"`; unknown names are reported in `skipped`, not errors. Import runs through the real `PUT /settings`, `PUT /projects/:id`, `PUT /presets/:id` and bench-set code paths, so the same validation applies. In `merge` mode a `null` setting in the file keeps the local value. `mode:"replace"` (an addition to the spec) additionally deletes projects, presets and bench sets not in the file and reports them in `removed`. The import route accepts bodies up to 2 MB and refuses `content` over 1 MB with 413. Errors are 400 for malformed YAML/JSON and unsupported versions.
- Not in scope and not implemented: chat-template editing (no portable backend API; the final prompt viewer shows what was sent).
- Real-backend smoke (LM Studio, `google/gemma-4-e4b` and `lfm2.5-24b-a2b`): a sequential compare of "Reply with the single word: pong" worked (gemma "pong", 2 tokens, decode ~31 tok/s, TTFT ~5.6 s incl. first-request load; lfm2.5 produced 64 tokens with empty visible content, i.e. the reasoning budget was consumed, decode ~20 tok/s). A benchmark (1 prompt, 2 targets, repeats 1, maxTokens 64) finished `done`, summary decode 24.1 tok/s (gemma) and 19.2 tok/s (lfm2.5), all metrics `source:"estimated"` (LM Studio streaming has no `stats`). A json_schema request against gemma through the server returned valid JSON with `jsonValid:true`.
